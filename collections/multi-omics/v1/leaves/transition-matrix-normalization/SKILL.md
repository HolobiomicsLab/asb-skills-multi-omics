# transition-matrix-normalization

## Summary

Normalize the supra-adjacency matrix of a constructed multiplex network into a transition matrix suitable for random walk with restart (RWR), as implemented by RWRtoolkit's compute.transition.matrix (RWR_make_multiplex pipeline) and benchmarked against the original RandomWalkRestartMH sequential implementation.

## When to use

Use when you have a supra-adjacency matrix from a multiplex network (e.g. L igraph layers from create.multiplex) and need a normalized transition matrix before running Random.Walk.Restart.Multiplex.

## When NOT to use

- Input is a single monoplex (non-multiplex) network that does not need supra-adjacency construction or per-layer tau weighting
- You only need aggregated (summarized) network analysis and are willing to lose the unique topological information carried by each layer
- You intend to change relative seed weighting rather than normalize the adjacency structure — the article notes tau in the original implementation weighted seeds equally across layers, a separate issue

## Inputs

- Multiplex network object: list of igraph layer objects from create.multiplex / RWR_make_multiplex
- flist file listing layer definitions as {file_path, name, group} triples
- Supra-adjacency matrix generated by compute.adjacency.matrix
- tau vector of per-layer restart weights

## Outputs

- Normalized transition matrix for the multiplex network
- RData multiplex object consumable by Random.Walk.Restart.Multiplex
- Benchmark timing table (e.g. multiplex_benchmark_timings.csv) if used in performance evaluation

## How to apply

First construct the multiplex network list of igraph objects via create.multiplex (or RWRtoolkit's RWR_make_multiplex using an flist of {file_path, name, group} triples), then generate the supra-adjacency matrix with compute.adjacency.matrix. Apply compute.transition.matrix, which normalizes the adjacency matrix to create a transition matrix; in the parallelized RWRtoolkit implementation the supra-adjacency computation can be distributed across cores (the benchmark used 32 cores), reducing construction of large multiplexes from hours to seconds (e.g. a 50-layer, 5000-node-per-layer grid combination completed in 17.69 s versus a 6-hour timeout for the original single-threaded RandomWalkRestartMH). The resulting transition matrix feeds directly into Random.Walk.Restart.Multiplex (the article ran 100 iterations). Correctness is judged by the matrix being row/column normalized to a valid stochastic form and by downstream RWR rankings being stable.

## Related tools

- **RWRtoolkit** (Provides compute.transition.matrix and parallelized compute.adjacency.matrix for multiplex supra-adjacency and transition-matrix construction) — https://github.com/dkainer/RWRtoolkit
- **RandomWalkRestartMH** (Original sequential implementation whose create.multiplex / compute.adjacency.matrix / compute.transition.matrix steps are normalized and benchmarked against) — https://github.com/alberto-valdeolivas/RandomWalkRestartMH

## Examples

```
Rscript run_make_multiplex.R --flist flist.tsv --tau "1.0,1.0,1.0" -o ./outdir
```

## Evaluation signals

- Transition matrix must be a valid stochastic (normalized) form of the supra-adjacency matrix — no zero-row or unnormalized columns
- Benchmark timing table must reproduce the reported contrast: original single-threaded construction exceeding the 6-hour limit while 32-core parallelized construction completes in approximately 17.69 s
- Multiplex object dimensionality matches the (L,N) grid combination used, e.g. L=50 layers of N=5000 nodes each plus inter-layer edges
- Downstream Random.Walk.Restart.Multiplex runs (100 iterations in the article) produce consistent rankings from the normalized matrix

## Limitations

- The original RandomWalkRestartMH multiplex construction was not optimized; computational load increases exponentially as network size and layer count grow, so sequential normalization is impractical for large multiplexes
- In the original RandomWalkRestartMH implementation, tau incorrectly weighted each seed equally across all layers, so transition/restart weighting must be checked when using the older package
- No version number is stated for RWRtoolkit or RandomWalkRestartMH in the article, so exact package versions must be pinned separately
